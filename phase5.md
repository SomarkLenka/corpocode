# CorpoCode — Phase 5 Implementation Specification

This document expands Phase 5, the final phase, of the master specification into a complete, self-contained build plan, in the same style as the Phase 1 through Phase 4 documents. It assumes Phases 1 through 4 are built and working, and it refers back to their pieces throughout. It also closes the series.

## What Phase 5 is, and why it is the finale

To understand Phase 5 you have to remember a decision made all the way back in Phase 1, because Phase 5 is the moment that decision pays off. From the very beginning, CorpoCode talked to its three kinds of knowledge — the code structure, the tiered reference material, and the experiential memory — only through interfaces, never through the tools that actually implemented them. Consumers called `KnowledgeGraph.scoreFiles` and `ContextStore.find` and `MemoryStore.recall`; they never knew or cared that, underneath, the knowledge graph was a Python tool called graphify spoken to over a child-process protocol, or that the context store was a daemon called OpenViking spoken to over HTTP. That indirection looked like extra ceremony at the time. Phase 5 is where it turns out to have been the whole point.

The external tools were always scaffolding. They let CorpoCode ship real capability quickly in the early phases without first having to build a multi-language code parser and a tiered vector store from scratch — enormous undertakings that would have delayed everything else. But scaffolding is meant to come down once the building can stand on its own, and two of those tools carry a cost that a finished product should not pay: they require an external Python toolchain to be installed, provisioned, and kept running alongside the npm package. Phase 5 removes that cost. It builds native TypeScript implementations of the knowledge graph and the context store, places them behind the exact same interfaces, makes them the default, and drops the Python toolchain from the install entirely. Because every consumer was written against the interface and not the implementation, not one line of the categorizer, the retrieval team, the context injector, or the compactor has to change. The swap is invisible from above. That invisibility is the thesis the entire five-phase plan was built to demonstrate.

It is worth noting what does *not* change, because it sharpens the point. The third knowledge abstraction, the memory store, has been native TypeScript since Phase 1 — it never used an external tool, so it needs nothing done to it here. Phase 5 simply brings the other two abstractions to where memory has been all along. When the phase is finished, all three are native, and CorpoCode's only hard runtime dependency is the cheap models behind the `Provider` abstraction that has powered it from the start.

The two principles that have governed every phase still hold. The dependency floor is the whole system, and in particular the `Provider` abstraction, which becomes the engine of the native implementations: the same provider that ranks candidates and runs checks will now also produce the summaries and embeddings that the native context store needs for its tiers, exactly as the native memory store has used it for embeddings since Phase 1. And the fail-open principle still holds, though Phase 5 actually *reduces* the number of ways things can fail, because an in-process library cannot be "down" the way a daemon can.

Because this is the last phase, there is nothing deferred beyond it. The sections below build the native knowledge graph, then the native context store, then flip the defaults and remove the Python toolchain while taking care not to strand anyone who depends on the old tools, and finally examine the footprint and performance of the resulting native engine. The document then closes by looking back over the whole plan.

## 1. The native knowledge graph

The first native implementation replaces graphify, and it lives in `src/backends/graph/native.ts`, behind the identical `KnowledgeGraph` interface that the graphify adapter implemented in Phase 1. The hardest part of building a code graph is parsing source code in many languages accurately and quickly, and the right tool for that job is tree-sitter, used here through web-tree-sitter — the WebAssembly build of tree-sitter that runs inside Node. Tree-sitter is the right choice for three reasons worth understanding: it has fast, well-maintained grammars for essentially every language a user is likely to write, it parses incrementally so re-parsing after a small edit is cheap, and it is error-tolerant, meaning it produces a usable syntax tree even from code that does not currently compile — which matters enormously, because an agent's working tree is very often in a half-finished, non-compiling state exactly when CorpoCode needs to understand it.

Building the graph means walking the repository, parsing each source file with the grammar for its language, and walking the resulting syntax tree to extract the nodes and edges the interface already defines. The nodes are the files, functions, classes, methods, and other symbols; the edges are the relationships between them — calls, imports, definitions, references, inheritance, and so on — each carrying the `Confidence` marker the interface specifies. That confidence field earns its keep here: the structure tree-sitter reads directly out of a file is `extracted` and certain, but a cross-file relationship like "this call refers to that function in another module" often has to be resolved heuristically, and is honestly marked `inferred` rather than presented as fact.

```typescript
// src/backends/graph/native.ts — building the graph from parsed syntax trees (sketch)
async function build(repoRoot: string): Promise<Graph> {
  const graph = new Graph();
  for (const file of await sourceFiles(repoRoot)) {
    const grammar = grammarFor(file);                 // load the web-tree-sitter grammar for this language
    if (!grammar) { graph.addOpaqueFile(file); continue; } // unsupported language → opaque file node, no crash
    const tree = grammar.parse(await read(file));     // error-tolerant: works even on non-compiling code
    // Walk the concrete syntax tree, emitting nodes for declarations and edges for relationships.
    // Structure read directly from the tree is "extracted"; cross-file resolution is "inferred" and marked so.
    walk(tree.rootNode, (decl) => graph.addNode(toGraphNode(decl, file)));
    walk(tree.rootNode, (ref) => graph.addEdge(resolveEdge(ref, graph)));
  }
  graph.computeCentrality();                           // degree/PageRank-style score so central files rank first
  return graph;
}
```

With the graph built, the interface methods become graph operations. `scoreFiles`, the method the categorizer's prefilter depends on, combines each file's structural centrality — a measure of how connected it is, so the files most likely to be central to a change rank highest — with relevance to the prompt, and it must produce the same deterministic ordering the graphify adapter did. `getNode`, `getNeighbors`, `findPath`, and `query` are traversals over the in-memory graph. The graph itself is persisted under the project's CorpoCode directory so it is not rebuilt from scratch on every process start; `ensureBuilt` builds it if no persisted graph exists, and `refresh` rebuilds it.

The freshness story is the native counterpart of something graphify already did, and it is what keeps the native graph viable on a large repository. Rather than re-parsing the whole tree on every change, the build registers a git hook — the same mechanism graphify used, now native — so that on each commit only the files that actually changed are re-parsed and their nodes and edges updated, using tree-sitter's incremental parsing. The expensive full parse happens once; everything after is a cheap delta. Languages without an available grammar degrade gracefully: the file becomes an opaque file node with no internal structure rather than causing an error, so an unusual language in a corner of the repo never breaks the build.

The proof that this native implementation is a true drop-in is that it must pass the very same structural conformance suite the graphify adapter passed in Phase 1 — the same fixtures, the same assertions about deterministic scoring and well-formed node, neighbor, path, and query results, the same `ping` semantics. If a consumer cannot tell from behavior which implementation it is talking to, the swap is genuinely invisible, which is exactly the standard to hold this to.

This section is done when the native knowledge graph builds a correct graph from a multi-language fixture repository, when its `scoreFiles` produces deterministic structurally-sensible rankings, when incremental refresh re-parses only changed files, when an unsupported language degrades to an opaque node rather than an error, and when the implementation passes the identical conformance suite the graphify adapter passed.

## 2. The native context store

The second native implementation replaces OpenViking, lives in `src/backends/context/native.ts`, and sits behind the identical `ContextStore` interface that the OpenViking adapter implemented in Phase 2. It has two jobs: to store reference material durably, and to serve it at the three levels of depth — the L0 abstract, the L1 summary, and the L2 full text — that the tiering is built around.

For storage, the native implementation uses an embedded database — SQLite is the natural default, with LMDB as an alternative for workloads dominated by simple key lookups — and the choice of an embedded database rather than a server is itself the largest part of the win. SQLite runs in-process, needs no daemon to start or keep alive, stores everything in a single file, and brings full-text search along for free, which gives the interface's `grep` a fast and correct implementation. Where OpenViking required a daemon on a port with its own configuration and lifecycle, the native store is just a file the process opens.

The more interesting question is where the tiers come from, because tiering was the thing OpenViking did with its own embedding and vision-language models. The native store produces the tiers itself, using the configured `Provider`. The full content is L2. A cheap-model pass over that content produces the L1 summary, and a further pass produces the one-line L0 abstract; and the embeddings that make `find` semantic rather than merely lexical are produced through the provider's embedding capability — the very same capability the native memory store has relied on since Phase 1. This is the through-line of the whole architecture made literal: the `Provider` abstraction is the muscle, and it powers the native context store's tiering exactly as it powers the categorizer's ranking and the memory store's recall.

```typescript
// src/backends/context/native.ts — tiering on write, powered by the Provider (sketch)
async function write(uri: string, content: string, opts?: { kind?: ResourceKind }): Promise<void> {
  // L2 is the full text; L1 and L0 are progressively shorter Provider-generated views of it.
  // Generated lazily on first access if you prefer to keep writes cheap — the compactor writes at Stop,
  // off the user's hot path, so eager generation here is also fine.
  const l2 = content;
  const l1 = await provider.summarize(l2, { target: "summary" });   // one cheap-model pass
  const l0 = await provider.summarize(l1, { target: "one-line" });  // a further cheap-model pass
  const embedding = await provider.embed(l1);                       // same embedding capability memory has used since Phase 1
  await db.put(uri, { kind: opts?.kind ?? "memory", l0, l1, l2, embedding });
}
```

The interface methods then map cleanly onto the database. `find` performs a tier-aware semantic search, escalating from L0 toward L2 as depth is needed, ranked by embedding similarity; `load` fetches a specific URI at a specific tier; `write` is the path the compactor uses at the `Stop` hook to land a session's distilled digest, generating the tiers as shown above; `tree` lists a subtree with each entry's L0 abstract; and `grep` is the full-text search. The `start` and `health` methods, which mattered for a daemon, become trivial here — `start` opens the database and `health` reports whether the file is openable — which is itself a sign of how much incidental complexity the native approach removes.

As with the graph, the proof of equivalence is the conformance suite: the native context store must pass the same round-trip suite the OpenViking adapter passed in Phase 2, exercising `find`, `load`, `tree`, and `write` across all three tiers and confirming that `health` reflects readiness. Passing it means the retrieval team and the compactor cannot tell they are now talking to a local database rather than a remote daemon.

This section is done when the native context store round-trips content through `find`, `load`, `tree`, and `write` at all three tiers; when its tiers and embeddings are produced through the configured provider; when `grep` is backed by full-text search; and when it passes the identical conformance suite the OpenViking adapter passed.

## 3. Flipping the defaults and dropping the Python toolchain

With both native implementations passing the same conformance suites as the tools they replace, the swap itself is almost anticlimactic, which is the best possible outcome. It comes down to changing two defaults. The `backends` block of the configuration, which has read `knowledgeGraph: "graphify"` and `contextStore: "openviking"` since the early phases, now defaults to `"native"` for both — `memoryStore` was already `"native"`. The factory functions `buildKnowledgeGraph` and `buildContextStore`, which have always selected an implementation by reading that block, now return the native implementations by default. And because every consumer in the entire system was written against the interface rather than the implementation, that is the complete extent of the change to the running system. Nothing in the categorizer, the retrieval team, the context injector, or the compactor is touched. This is the moment the Phase 1 investment in abstraction is repaid in full.

The other half of the work is removing the Python toolchain from the install. The installer's backend-provisioning steps that installed graphify and provisioned and started the OpenViking daemon are no longer run for a default install, so the install footprint shrinks to the npm package and its single bundled binary, with no external runtime to fetch or maintain. The `doctor` checks follow suit: the Python-toolchain check, the graphify-server check, and the OpenViking-daemon check are no longer unconditional. They become conditional, running only if a configuration explicitly selects a Python-backed backend, and in their place `doctor` gains native checks that confirm the graph is built and the database opens.

It would be a mistake, though, to strand the users who adopted CorpoCode in its earlier phases and built workflows around graphify or OpenViking, and the abstraction makes it unnecessary to strand them. The graphify and OpenViking adapters remain in the codebase as fully supported, selectable alternatives — they are, after all, just two more implementations behind the same interfaces. A user who deliberately sets `knowledgeGraph: "graphify"` keeps exactly the behavior they had, and `doctor` still runs the Python and daemon checks for them precisely because their configuration asks for those backends. What changes for such a user is only that the install no longer provisions those tools automatically; they provision them themselves, as an explicit choice. The native backends are the default and the recommended path, but the old ones are a supported option, not a removed feature.

Migration for existing installs is mercifully simple, and the reason is a property the system has had all along: the repository is the source of truth for the code graph, and the repository and transcripts are the source of truth for the context store, so both native backends can always be rebuilt from scratch with no precious, unrecoverable state to migrate. An upgrade therefore needs only to build the native graph once with `ensureBuilt` and to let the context store re-tier material as it is next written and read; the `corpocode upgrade --refresh-deps` command drives this, building the native backends in place of the old behavior of rebuilding the Python ones. A user upgrades, the graph builds, and everything proceeds — no data export, no import, no manual step beyond the rebuild.

This section is done when a default configuration selects the native backends and a full turn runs end-to-end with no Python process and no daemon present; when a fresh install provisions no Python toolchain and starts no daemon; when `doctor` omits the Python and daemon checks under a native configuration and includes them only when a Python-backed backend is explicitly selected; when a user who explicitly selects graphify or OpenViking still works with those tools; and when an upgrade builds the native graph and re-tiers context without any manual data migration.

## 4. The footprint and performance of the native engine

Going native changes the system's shape, and it is worth being clear-eyed about both what it gives and what it asks in return, because the trade is the substance of this phase. What it gives is substantial. There is no daemon to start, so the cold-start path is shorter. There are no cross-process hops — no child-process protocol to graphify, no HTTP round-trip to OpenViking — so every knowledge call avoids the latency of inter-process communication and simply runs in memory. There is no Python runtime to install, version, or keep compatible, so the install is smaller and there are fewer moving parts to break. And the entire system is now one language, which makes it easier to maintain, debug, and reason about end to end.

What it asks in return is that the work those external tools used to do in their own processes now happens inside the same Node process that serves the hooks, which means it must live within the latency budgets and the caching discipline established in Phase 4. The honest way to manage this is to keep the expensive work off the per-turn hot path, and the design already does. The one genuinely expensive operation is the initial full parse of the repository to build the graph, and that happens exactly once, through `ensureBuilt`, and is then kept current by the incremental git-hook refresh rather than ever being repeated wholesale. The provider-driven tiering of context happens on `write`, which the compactor performs at the `Stop` hook in the background, after the user's turn is already complete. What remains on the per-turn hot path — `scoreFiles` and the graph traversals during retrieval — are fast in-memory operations, and they are subject to the same caching, keyed on the graph's version, that Phase 4 introduced. The result is that the user feels the native engine as faster, not slower, because the heavy work has been pushed to build time and background time where it belongs.

The operational surfaces shift accordingly but stay familiar. `doctor` now reports the health of the native backends — whether the graph is built and the database opens — rather than the reachability of daemons, and `stats` is entirely unchanged, since cost and latency still flow through the same provider calls and the same NDJSON log they always have. The reliability picture quietly improves: the fail-open and resilience patterns from the earlier phases still apply, but there is simply less that can go wrong, because a native library is either present and working or rebuildable on demand, and never in the ambiguous state of a daemon that has crashed or wandered off.

This section is done when a full turn under the native backends stays within the Phase 4 latency budgets at the median and the tail; when the initial graph build is confined to build time and incremental refresh keeps it current without full rebuilds; when provider-driven tiering runs in the background at `Stop` rather than on the hot path; and when `doctor` and `stats` report correctly against the native engine.

## Definition of done for Phase 5

Phase 5 is complete when all of the following hold, which together form the acceptance criteria for the phase.

The native knowledge graph is a true drop-in: it builds a correct multi-language graph through web-tree-sitter, scores files deterministically and sensibly, refreshes incrementally on changed files via a git hook, degrades gracefully on unsupported languages, and passes the identical conformance suite the graphify adapter passed in Phase 1. The native context store is likewise a true drop-in: it stores material in an embedded database, produces its L0, L1, and L2 tiers and its embeddings through the configured provider, backs `grep` with full-text search, and passes the identical conformance suite the OpenViking adapter passed in Phase 2. The defaults are flipped and the toolchain is gone: a default configuration selects the native backends, a full turn runs end-to-end with no Python process and no daemon, a fresh install provisions neither, and `doctor` includes the Python and daemon checks only when a Python-backed backend is explicitly selected. No one is stranded: the graphify and OpenViking adapters remain selectable for users who want them, and an upgrade rebuilds the native graph and re-tiers context with no manual data migration. And the native engine performs: the heavy parsing and tiering stay at build time and background time, the per-turn path remains within the Phase 4 budgets, and `doctor` and `stats` report correctly.

When all of that holds, CorpoCode stands entirely on its own. All three of its knowledge abstractions are native TypeScript, its install is a single npm package with no external runtime, and its only hard dependency is the cheap models that have driven it since the first hook fired.

## Closing the series

It is worth stepping back, now that the plan is complete, to see the shape of the whole thing, because each phase only fully makes sense in light of where it was leading. Phase 1 built the foundation and the senses: a multi-provider, fully observable system that could read the model's line of thought and inject a single advisory recommendation, but that was deliberately forbidden from acting until its plumbing had earned trust. Phase 2 gave it hands and a memory: the power to deny a dangerous command, halt a design-violating edit, assemble precise context from three kinds of knowledge, reshape a file read — and, most importantly, to write down what it learned so each session could improve the next. Phase 3 gave it reach and craftsmanship: it spread across the major coding-agent platforms through one thin adapter and began leaving durable artifacts behind — a clean git history distilled from the torrent of edits, documentation grounded in the real call graph, reusable skills mined from memory — all while keeping consequential changes under the user's control. Phase 4 turned the capable tool into a public product and an ecosystem: an inert, trustworthy install, opt-in and aggregate-only telemetry, a plugin API that lets a community extend the retrieval and the design checks, the performance to feel invisible, and the documentation to be understood. And Phase 5 removed the last scaffolding, replacing the borrowed Python tools with native engines behind the same interfaces, so that the finished system depends on nothing but the cheap models at its core.

The single idea that runs through all five phases, and that the last one makes undeniable, is the discipline of building against interfaces rather than implementations. It is what let Phase 1 ship quickly on borrowed tools, what let every component in Phases 2 through 4 be written once and never revisited, and what let Phase 5 swap the entire knowledge substrate without disturbing a single consumer. The whole arc — a system that watches a developer think, fetches and checks and remembers on their behalf, and runs an army of cheap models to spare one expensive one — rests on that quiet architectural decision more than on any single feature. That is the plan, end to end.
