# CorpoCode — Phase 4 Implementation Specification

This document expands Phase 4 of the master specification into a complete, self-contained build plan, in the same style as the Phase 1 through Phase 3 documents. It assumes Phases 1 through 3 are built and working, and it refers back to their pieces throughout.

## What Phase 4 is, and how it changes the system

It is worth pausing on the arc before describing the destination. Phase 1 gave CorpoCode senses, Phase 2 gave it hands and a memory, and Phase 3 gave it reach across platforms and the craftsmanship to leave durable artifacts behind. After all three, CorpoCode is a genuinely capable tool — but it is still, in an important sense, a *private* one. It is installed by people who already know it exists, it is extended only by editing its own source code, and it improves only from the logs and memory of the single person running it. Everything works, but nothing about it is yet built for strangers.

Phase 4 is the phase that turns a capable private tool into a public product and the beginning of an ecosystem. It does four things, and they correspond to the four things a tool needs before thousands of people who have never met its authors can depend on it. It brings the public npm release and its automated pipeline live, so that anyone can install it with a single command. It adds opt-in telemetry, so that the project can learn from real-world usage in aggregate — while treating the protection of the user's data as the non-negotiable constraint that shapes the entire design. It opens a plugin API, so that other people, not only the core team, can ship their own retrieval templates and their own design tenets, discovered automatically at startup. And it does the performance and documentation work that separates "works on my machine" from "works, quickly and understandably, for people I will never meet."

As in every prior phase, two rules carry forward, and one of them sharpens into the theme of this phase. The dependency floor is the whole system built so far: the release pipeline was scaffolded in Phase 1, when you placed a `.releaserc` and adopted semantic-release; the telemetry configuration block was declared in Phase 1's schema as `telemetry` with `enabled` defaulting to false; the two plugin extension points are the retrieval templates from Phase 2's planner and the MOLAR-EDIT tenets from Phase 2's verifier and design-review team; and the performance work targets the many cheap-model calls and the per-hook process startup that have been present throughout. The fail-open principle still holds everywhere. But the governing idea of this phase is a sharpening of Phase 3's control principle into something broader: where Phase 3 said *the user stays in control of durable changes*, Phase 4 says *the user's data and trust are protected as the product goes public*. A private tool can assume a single trusting user; a public product must earn the trust of strangers, and that obligation is what makes telemetry opt-in and aggregate-only, what keeps a fresh install inert until the user deliberately activates it, and what makes the plugin surface declarative and transparent rather than a blank cheque to run arbitrary code.

One thing remains deferred, and it is the architectural finale: Phase 5 replaces the Python-backed knowledge graph and context store with native implementations and drops the external toolchain entirely. Phase 4 is the last phase concerned with the product and its ecosystem; Phase 5 is concerned with the engine underneath.

The sections below run in a natural order: first the release that makes CorpoCode public at all, then the telemetry that lets the project learn from real use, then the plugin API that lets others extend it, then the performance pass that makes it fast at scale, and finally the documentation site that teaches people to use and extend it.

## 1. The public npm release and its pipeline

The first task is to make `corpocode` something a stranger can install, and to make releasing it an automated, trustworthy, repeatable act rather than a manual ritual. Most of the machinery for this was put in place in Phase 1 and only needs to be brought to life: the package already bundles to a single `bin/corpocode.js` through esbuild, it already declares its binary and its Node floor, and it already carries a `.releaserc` for semantic-release. Phase 4 connects these into a working pipeline.

The release pipeline is driven by commit messages, which is what makes it repeatable. Following the Conventional Commits convention, semantic-release reads the commits merged to the main branch, decides the correct semantic-version bump from their types — a fix is a patch, a feature is a minor, a breaking change is a major — generates a changelog from those same messages, publishes the package to npm, tags the commit, and writes the release notes. The value of this is that a human never decides a version number by hand and never forgets a changelog entry; the discipline lives in the commit messages, where it belongs.

A release must not publish something broken to strangers, so the pipeline gates publication on the full verification suite running across the environments real users have. The continuous-integration matrix runs the install, the `doctor` checks, and the provider and backend conformance suites from the earlier phases on Node 20 and Node 22 across macOS, Linux, and Windows, and a failure on any cell blocks the publish. This is simply the acceptance criteria you have been accumulating phase by phase, now wired up as a release gate rather than a manual checklist.

There is one safety property here that matters more than any other, and it is easy to get wrong because the convenient thing is also the dangerous thing. Installing the package from npm must be *inert*. Running `npm install -g corpocode` should do nothing but place the binary on the user's path. It must not register hooks into any platform, must not provision or start the graphify or OpenViking daemons, must not write a configuration file, and must not contact the network. All of that activation happens only when the user deliberately runs `corpocode install`, which they do with full knowledge of what it will do. The reason for the strict separation is that a package whose mere installation reaches into your editor's settings, spawns background daemons, or phones home is exactly the kind of package a careful engineer learns to distrust. CorpoCode earns trust by doing nothing surprising at install time; the powerful, system-touching work is gated behind an explicit, separate, documented command. Concretely, this means there is no `postinstall` script that does any of those things.

The remaining release concerns are matters of supply-chain hygiene appropriate to a public package: a committed lockfile so builds are reproducible, published provenance so consumers can verify the package was built from the source it claims, a deliberately minimal dependency surface so there is less to audit and less to break, and a files allowlist so that only the bundled binary and the assets it needs are shipped rather than the whole source tree and test suite. Because the configuration schema is now something strangers depend on, it must be versioned, and any release that changes the schema must either migrate an old configuration forward or tolerate it, so that an upgrade never breaks a user who has not touched their config.

This section is done when a merge to the main branch triggers an automated version bump, changelog, and npm publish; when the published package installs cleanly across the full Node-and-operating-system matrix; and when a fresh `npm install` is demonstrably inert — registering no hooks, provisioning no daemons, writing no config, and making no network request — until `corpocode install` is run.

## 2. Opt-in telemetry

Telemetry is how a project learns whether its choices are working in the real world: whether the cheap models really are saving more than they cost, which classifications get overridden, where the latency actually goes. But telemetry is also the feature most capable of betraying a user's trust, and so the entire design here is shaped by a single constraint — protect the user's data absolutely — rather than by what would be most informative to collect. The configuration block was declared back in Phase 1 with `enabled` defaulting to false, and that default is the foundation of everything that follows.

The first and most important property is that *off means off*. When telemetry is disabled, which is the default for every install, CorpoCode makes zero network requests of any kind across an entire turn. There is no "anonymous ping," no "just checking for updates," nothing. A user who never opts in is never observed, and this is verifiable: a full turn under the default configuration produces no egress whatsoever.

Enabling telemetry is a deliberate act. The user turns it on explicitly, through their configuration or a `corpocode telemetry on` command that first explains exactly what will and will not be collected, so that consent is informed rather than buried. And what is collected is defined by a whitelist, not a blacklist — only an explicitly enumerated set of aggregate, non-identifying fields is ever transmitted, which is a stronger guarantee than trying to strip sensitive data out of a richer payload. The collected fields are things like anonymized counts of hook invocations, the distribution of model and effort choices, the cost-savings estimate the tracker already computes, error rates, which backends are in use, and latency percentiles. The fields that are *never* collected are the ones that could identify the user or expose their work: prompts, code, file contents, file paths, transcripts, the contents of memory, the identity of the repository, and anything else from which a person or a project could be recognized. The line is bright and it is drawn on the side of caution.

Because telemetry must never be silently on, `doctor` displays a clear banner whenever it is enabled, stating that telemetry is active and pointing to the documentation of exactly what is collected. The transport itself is batched and infrequent so that it imposes no per-turn cost, and it is fail-open in the same sense as everything else in the system: a failed telemetry send is swallowed and never affects the turn the user is in. And to make the guarantee inspectable rather than merely promised, a `corpocode telemetry preview` command shows precisely the payload that would be sent, so a skeptical user can see for themselves that it contains only the whitelisted aggregate fields.

The way to think about this whole design is that it mirrors, deliberately, the privacy posture a careful system applies to its own users: collect the minimum, never the sensitive, default to off, and make the whole thing visible. Telemetry that follows those rules is something a project can ethically ship and a user can reasonably allow.

This section is done when the default configuration produces zero network egress across a full turn; when enabling telemetry transmits only the documented whitelist of aggregate fields and nothing else, verifiable through the preview command; when `doctor` shows the banner whenever telemetry is on; and when a telemetry transport failure never affects a turn.

## 3. The plugin API

A tool the core team alone can extend will only ever be as rich as the core team's time allows. A tool that strangers can extend can grow in directions its authors never imagined. Phase 4 opens CorpoCode to that kind of growth, and it does so at exactly the two seams the architecture was designed to be extended along: the retrieval templates that tell the retrieval team what to gather for a given kind of task, and the MOLAR-EDIT tenets that tell the verifier and the design-review team what to check. These were always the pluggable parts; Phase 4 makes plugging in them a public, supported act.

The mechanism is package naming, the same convention-based discovery that ecosystems like ESLint and Babel use to good effect. A package named `corpocode-template-*` contributes one or more retrieval checklist templates — the per-task-type templates that Phase 2's planner selects among — and a package named `corpocode-tenet-*` contributes one or more `TenetCheck` families to the verifier and design-review fan-out. At startup, CorpoCode scans the installed packages, finds the ones whose names match these conventions, loads them, and registers their contributions. The naming convention is itself the discovery mechanism, which means a user adds a capability simply by installing a package, with nothing to wire up by hand.

What a plugin exports is a stable, versioned contract, and keeping that contract declarative is a deliberate safety choice. A plugin contributes *definitions* — template structures and check definitions — rather than arbitrary imperative behavior, so that installing a plugin extends the data CorpoCode reasons over without handing the plugin free rein to do anything it likes in the user's environment.

```typescript
// src/plugins/types.ts — the public, versioned contract a plugin package exports
export interface CorpoPlugin {
  readonly apiVersion: 1;                 // plugins declare which API generation they target
  readonly name: string;
  templates?: RetrievalTemplate[];        // contributed by corpocode-template-* packages
  tenets?: TenetCheck[];                  // contributed by corpocode-tenet-* packages (see the MolarEditEngine types)
}

// src/plugins/discover.ts — convention-based discovery at startup (sketch)
async function discoverPlugins(): Promise<CorpoPlugin[]> {
  const candidates = await installedPackagesMatching(/^corpocode-(template|tenet)-/);
  const loaded: CorpoPlugin[] = [];
  for (const pkg of candidates) {
    try {
      const plugin = await loadPlugin(pkg);          // import the package's default export
      if (plugin.apiVersion === 1) loaded.push(plugin); // ignore plugins built for an incompatible API generation
    } catch {
      // A plugin that fails to load is skipped, not fatal — the same fail-open rule as everywhere else.
      logSafely(`plugin ${pkg} failed to load; skipping`);
    }
  }
  return loaded;
}
```

Two properties keep this safe and honest. The first is transparency: `doctor` lists every discovered plugin and what it contributes, so the user can always see exactly what is extending their CorpoCode rather than wondering why a new retrieval template or design check has appeared. The second is the fail-open rule applied to extensions: a plugin that throws while loading is skipped rather than allowed to crash CorpoCode, and a contributed template or check that misbehaves at runtime degrades the same way a built-in one would — the broken item is dropped and the turn proceeds. And because the contract carries an `apiVersion`, a plugin built against an older or newer generation of the API can be recognized and declined cleanly rather than loaded into incompatibility.

This section is done when a `corpocode-template-*` package and a `corpocode-tenet-*` package each auto-register at startup and appear in `doctor`; when their contributions are actually exercised — the contributed template can be selected by the planner and the contributed check runs in the verifier fan-out; and when a deliberately broken plugin is skipped rather than crashing CorpoCode.

## 4. Performance

Everything CorpoCode does, it does by making cheap-model calls, and it pays a fresh Node process startup on every hook the platform fires. For a single user on their own machine, the latency and cost of this are easy to absorb. For a product that thousands of people run on every turn of their work, the same costs become the difference between a tool that feels invisible and one that feels like a tax. Phase 4 is where the cost and latency that the earlier phases tracked become something the project actively disciplines and budgets.

The cold-start cost is already mitigated by a decision made in Phase 1 — bundling everything into a single file with no dependency resolution to do at runtime — and Phase 4's job is to measure it, set a budget for it, and hold the line. The most consequential budget is the latency that the `UserPromptSubmit` hook adds before the model sees its recommendation, because that delay sits directly between the user pressing enter and the model beginning to respond; it must stay small at both the median and the tail.

Caching is the largest lever, and the principle is to never pay twice for the same answer within a window where the answer cannot have changed. The session reader already caches its distilled state per session, and Phase 4 extends the same idea to the other expensive, repeatable computations: graph file-scoring keyed on the prompt and the graph's version, embeddings keyed on their text, and provider responses where the inputs are identical and the call is safe to memoize. Each cache is keyed on something that genuinely invalidates it — a new graph build invalidates graph-derived caches, for instance — so a cache hit is always a correct answer and never a stale one.

Concurrency must be globally bounded, not just locally. The retrieval fan-out already caps its parallel instances and the verifier fans out across tenets, but Phase 4 ensures these are governed by a sensible global budget, so that no single turn can spawn an unbounded swarm of simultaneous model calls that would blow past rate limits or spike cost. And every component must respect its latency budget by degrading rather than blocking: when a component exceeds its budget, the fail-open rule applies and it returns whatever it has rather than making the user wait, which is why the per-item and per-check timeouts established in Phase 2 matter as much for performance as for resilience.

Finally, the central premise of the whole project — that cheap models save more expensive-model time than they themselves cost — is something Phase 4 validates at scale rather than assuming. The cost tracker and `stats` from Phase 1 already produce the raw numbers; Phase 4 adds latency percentiles and a performance view, and uses that data to tune the default model-per-component choices so the savings ratio stays comfortably favorable across real workloads.

This section is done when the latency added by each hook stays within a stated budget at both the median and the tail; when caching demonstrably reduces the cost and latency of repeated computations without ever serving a stale result; when concurrency is bounded by a global budget; and when a component that exceeds its budget degrades cleanly rather than blocking the turn.

## 5. The documentation site

A public product that cannot be understood will not be adopted, and a plugin API that is not documented will not be built against. The documentation site is therefore not an afterthought but the surface through which the entire system becomes legible to the people who did not build it. It serves three audiences, and it is worth being explicit about each because they need genuinely different things.

End users need to know how to install CorpoCode, how to configure it, what each command does, and — just as importantly — what the tool is actually trying to do for them, because a tool that injects context and reshapes file reads is far easier to trust when its philosophy is explained rather than hidden. Plugin authors need the plugin API documented in full: the contract a `corpocode-template-*` or `corpocode-tenet-*` package implements, a worked example of writing each kind, and the rules of the road around versioning and the fail-open behavior. Contributors need the architecture explained: the three caretakers, the four abstractions, and the data flow that connects them, which are precisely the things the prospectus and these phase specifications describe.

The content the site must cover follows from those audiences. It needs the conceptual model of the caretakers and the abstractions; a complete configuration reference; a complete command reference; an explanation of the MOLAR-EDIT philosophy and its nine tenets; the plugin authoring guide; the platform support matrix, carrying forward the honest caveat from Phase 3 that the precise integration details for each platform are confirmed at implementation time; and a plain, prominent disclosure of the privacy and telemetry posture, so that the opt-in, aggregate-only design is something a prospective user can read and verify before they ever enable it.

There is one principle borrowed directly from Phase 3's documentation generator and turned on CorpoCode's own docs: generate the reference material from the source wherever possible so it cannot drift. The configuration reference should be derived from the Zod schema that already defines the configuration, and the command reference from the CLI definitions that already define the commands, so that when the code changes the documentation changes with it rather than quietly falling out of date. Stale documentation is worse than none, and the cure is the same here as it was for the code: tie the docs to the source.

This section is done when the site documents installation, configuration, every command, the philosophy, and the plugin API; when it discloses the privacy and telemetry posture plainly; and when the configuration and command references are generated from the source rather than maintained by hand.

## Definition of done for Phase 4

Phase 4 is complete when all of the following hold, which together form the acceptance criteria for the phase.

The public release works and is trustworthy: a merge to the main branch produces an automated version bump, changelog, and npm publish; the published package installs cleanly across Node 20 and 22 on macOS, Linux, and Windows, gated by the full conformance and `doctor` suite; and a fresh `npm install` is inert, touching no settings, provisioning no daemons, writing no config, and making no network request until `corpocode install` is run. Telemetry protects the user by construction: the default configuration produces zero network egress across a full turn, enabling it transmits only the documented whitelist of aggregate fields and nothing identifying, the `telemetry preview` command makes that payload inspectable, `doctor` shows a banner whenever telemetry is on, and a transport failure never affects a turn. The plugin API opens the two intended seams: a `corpocode-template-*` package and a `corpocode-tenet-*` package each auto-register at startup and appear in `doctor`, their contributions are actually exercised by the planner and the verifier, and a broken plugin is skipped rather than fatal. Performance is disciplined: each hook's added latency stays within budget at the median and the tail, caching reduces repeated cost and latency without serving stale results, concurrency is globally bounded, and budget overruns degrade rather than block. And the documentation site makes the whole system legible: it covers installation, configuration, commands, philosophy, and the plugin API, it discloses the privacy posture plainly, and its references are generated from source.

When all of that holds, CorpoCode is a public product rather than a private tool. Anyone can install it with one inert, trustworthy command and activate it deliberately; the project can learn from real usage without ever compromising a user's data; a community can extend its retrieval and its design checks by publishing packages that register themselves; it runs quickly enough at scale to feel invisible; and it is documented well enough that strangers can both use it and build on it. Only one tie to the outside world remains. CorpoCode still depends on an external Python toolchain for two of its three knowledge abstractions — the graphify-backed knowledge graph and the OpenViking-backed context store — while its memory has been native since the very beginning. Phase 5 is the architectural finale that removes that last dependency: it builds native TypeScript implementations of the knowledge graph, using web-tree-sitter for parsing, and of the context store, using an embedded database with Provider-driven tiering; it flips the `backends` defaults from the external tools to the native ones; and it drops the Python toolchain from the install entirely, leaving a system whose only hard dependency is the cheap models that have powered it from the start.
